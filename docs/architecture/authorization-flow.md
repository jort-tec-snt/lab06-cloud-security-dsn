# Flujo de autorización de documentos

Cada ruta de documentos ejecuta **authenticate → RBAC → cargar o construir recurso → ABAC → operación → auditoría**. `GET /auditoria` usa authenticate → RBAC → construir consulta filtrada → lectura → auditoría; no hay documento sobre el que aplicar ABAC. Un fallo en cualquier paso se registra como denegado (o error interno) antes de responder. El registro se escribe mediante `recordAudit`, que también recibe los rechazos de token ausente, inválido o revocado y usuario inactivo o suspendido.

`authenticateRequest` verifica firma, vigencia, emisor, audiencia, revocación y estado vigente del usuario en PostgreSQL. `getEffectivePermissions` lee las asignaciones RBAC actuales de PostgreSQL en cada petición. Los códigos requeridos son `CONSULTAR_DOCUMENTO`, `CREAR_DOCUMENTO`, `MODIFICAR_DOCUMENTO`, `ELIMINAR_DOCUMENTO`, `APROBAR_DOCUMENTO` y `VER_AUDITORIA` según la ruta. Un rechazo RBAC impide cargar el documento.

El recurso se obtiene por UUID tras RBAC. Un UUID inexistente devuelve `404` sin datos del recurso. POST construye un candidato `PENDIENTE` cuyo `propietarioId` procede exclusivamente del JWT verificado. PUT valida campos permitidos con Zod, comprueba ABAC sobre el documento actual y sobre el candidato resultante; así no puede usar una edición para rebajar un documento inaccesible ni elevar su nivel o cambiarlo de departamento indebidamente. El estado solo cambia mediante `/aprobar`, de `PENDIENTE` a `PUBLICADO`. Los cuerpos no admiten `propietarioId` ni `estado`.

`authorizeLoadedDocument` consulta las ocho políticas existentes. Para POST usa la acción `CREAR_DOCUMENTO` con ese mismo registro; no se agregan ni modifican políticas. En `GET /documentos`, se evalúa cada documento antes de añadirlo al resultado. Los denegados se omiten por completo; se registra cada evaluación de documento, permitida o denegada, además del acceso al listado. Las respuestas 403 distinguen `RBAC_DENIED` y `ABAC_DENIED`; el motivo persistido indica permiso o política, condición, valor esperado y detectado. Los errores AUTH conservan un motivo interno específico sin revelar detalles del token en la respuesta.

El servicio de auditoría guarda usuario cuando se conoce de forma verificable, recurso, acción, fecha real, resultado, motivo, IP de Express, ubicación y dispositivo. La IP procede de la conexión directa (`trust proxy` desactivado). En producción, ubicación y dispositivo quedan `DESCONOCIDA` y `DESCONOCIDO` hasta integrar fuentes verificadas. La consulta de auditoría es solo lectura, exige `VER_AUDITORIA` y permite `resultado`, `usuario` (UUID), `accion`, `limite` (1–100) y `pagina` (1–10000), validados por Zod. No hay rutas para editar o eliminar registros.

`DEMO_MODE=true` solo tiene efecto cuando `NODE_ENV` es distinto de `production`. Acepta `X-Demo-Hour` (hora 0–23 en Lima), `X-Demo-Location` (país en mayúsculas) y `X-Demo-Device` (`CORPORATIVO` o `PERSONAL`) con validación estricta. Es exclusivo de desarrollo local; el futuro frontend deberá indicar de forma explícita cuándo está activo. En producción esas cabeceras se ignoran. La fecha de auditoría siempre usa el reloj real, incluso durante una demostración.
